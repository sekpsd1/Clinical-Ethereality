# Purge stuck UAT consultations

This operator-only command permanently removes exactly three `live` consultations for one explicitly selected test customer. It preserves the customer account, shared assessments, and exactly two `scheduled` consultations. It has no admin UI and is dry-run by default.

## Safety boundary

- Supply the exact test customer selector only through `ADMIN_PURGE_UAT_LINE_USER_ID`. The value is never printed.
- Dry-run output contains only an opaque SHA-256 fingerprint and aggregate counts.
- Related notifications are selected only for the target customer/assigned doctors and relevant types, then matched by an exact parsed `metadataJson.consultationId`. Exact Zoom handoff ticket/session markers are scoped to the same customer or assigned doctor; ordinary login sessions are never selected.
- Execute mode refuses any target other than exactly three `live` consultations and exactly two preserved `scheduled` consultations for the same customer.
- Execute mode requires the dry-run fingerprint, every expected aggregate count, an exact database host/name boundary, the production confirmation phrase, and a verified backup no older than 60 minutes.
- Zoom recording IDs must map exactly to the scoped database metadata. Missing credentials/scopes or any provider mismatch fails closed before file or database deletion.
- Every attachment directly tied to a target consultation, payment, or prescription is inventoried. Supported payment evidence must be exclusively referenced, owned by the target customer/payment, inside `PAYMENT_UPLOAD_DIR`, a non-symlink regular file, and match stored size and image magic. The ownership guard accepts only the three private paths generated by the application: an existing Payment ID, the exact Consultation provisional path proven by that Payment's private-file submission marker, or the exact Admin manual-appointment provisional path proven by matching Payment, attachment, Doctor, appointment time, and intake metadata. A legacy Consultation marker may omit `submittedAt` only when exactly one scoped `consultation.private_slip_uploaded` audit row binds that same Consultation, Payment, attachment, and pending-review transition; a present but malformed timestamp is never treated as legacy. This preserves compatibility with application-generated private paths without weakening ownership checks. Unknown, ambiguous, or mismatched attachment ownership/purpose/storage/audit evidence fails closed.
- Normal execute mode requires every expected Zoom recording and private file to exist. Only explicit `--resume=<original-fingerprint>` mode may accept an expected provider subset or missing private file after a failed partial attempt; any unexpected provider ID still fails closed.
- Provider and private-file deletion happen before one serializable database transaction. Any failure is reported as failure. A retry revalidates the same scope and completes the remaining work.
- Logs and reports must never include customer/consultation/payment/recording IDs, paths, URLs, payloads, or secrets.

## Dry-run

Set `DATABASE_URL` and `ADMIN_PURGE_UAT_LINE_USER_ID` in the operator environment, then run:

```powershell
npm run admin:purge-stuck-uat-consultations
```

The earlier read-only preflight established this baseline:

```json
{"liveConsultations":3,"scheduledConsultations":2,"liveConsultationDays":2,"attendanceCredentials":11,"attendanceEvents":0,"messages":0,"recordings":15,"recordingWebhookEvents":5,"telemedicineConsents":3,"payments":3,"prescriptions":0,"slotLocks":3,"privateAttachments":3,"directAuditRows":65}
```

The expanded dry-run also reports `otherScopedAttachments`, `relatedNotifications`, and `zoomHandoffSessions`. Review those new aggregate counts, stop if any established baseline count differs, and pass the complete counts object returned by that same dry-run to execute mode. Do not copy raw database or provider records into tickets, chat, or logs.

## Execute gate

Execution is a separate, explicitly reviewed production operation. Before it, create and verify both a fresh database backup and a fresh private-file backup using the approved infrastructure procedure. Set these values in the operator environment without committing them:

- `ADMIN_PURGE_BACKUP_VERIFIED=true`
- `ADMIN_PURGE_BACKUP_REFERENCE=<opaque backup reference>`
- `ADMIN_PURGE_BACKUP_CREATED_AT=<ISO-8601 timestamp>`
- `ADMIN_PURGE_FILE_BACKUP_VERIFIED=true`
- `ADMIN_PURGE_FILE_BACKUP_REFERENCE=<opaque private-file backup reference>`
- `ADMIN_PURGE_FILE_BACKUP_CREATED_AT=<ISO-8601 timestamp>`
- `PAYMENT_UPLOAD_DIR=<absolute private payment storage root>`
- the existing Zoom Server-to-Server OAuth credentials, after separately granting/verifying only the minimum recording-file deletion scope required by Zoom

Run execute mode only with the exact values returned/verified by the immediately preceding dry-run:

```powershell
npm run admin:purge-stuck-uat-consultations -- --execute --confirm=<64-character-fingerprint> --expected-counts=<single-line-json> --expected-host=<database-host> --expected-database=<database-name> --confirm-production=PURGE_STUCK_UAT_LIVE_ONLY
```

Success is reported only after aggregate verification confirms zero scoped live consultations/dependencies, two scheduled consultations, and the retained customer account. If the command fails after provider or file deletion, keep the backup and rerun the complete command with a fresh dry-run and confirmation; do not manually edit the database.

For a retry after the command reports a partial external-deletion failure, use the unchanged database fingerprint from a fresh dry-run as both `--confirm` and `--resume`:

```powershell
npm run admin:purge-stuck-uat-consultations -- --execute --confirm=<fingerprint> --resume=<same-fingerprint> --expected-counts=<complete-single-line-json> --expected-host=<database-host> --expected-database=<database-name> --confirm-production=PURGE_STUCK_UAT_LIVE_ONLY
```

Never use `--resume` for the initial execution. It is accepted only with all normal execute gates, a fresh verified backup, and an unchanged database fingerprint.
